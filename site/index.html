GKE as code, with the Kubernetes parts run for real.

Terraform for GKE Standard and Autopilot clusters, Workload Identity, a private network, autoscaling, RBAC, stateful recovery, ingress and CI/CD. The manifests run on a kind cluster in CI: the HPA scales under load, the VPA gives a recommendation, RBAC denials are asserted, and a StatefulSet is wiped and restored. Standard or Autopilot

Both are in terraform/envs/dev. The choice is about who owns the nodes, and it changes which autoscaler you tune.

QuestionStandardAutopilot
Who sizes nodes?You: machine type, pool bounds per zone, upgrade surge.Google. No node pool resource exists.
What do you pay for?Nodes, used or not.Pod resource requests, so requests are the cost control.
Cluster AutoscalerSet min and max per zone on the pool. Tuned here with BALANCED and surge 1, unavailable 0.Not yours to tune. Nodes appear to fit pending pods.
DaemonSets, privileged agents, GPUsAllowed.Restricted.
I would choose it whenA workload needs a node-level agent, or bin packing is the cost lever.The team wants requests to be the only knob. This is the default for ordinary services.

Cost: Standard leaves empty capacity if the pool minimum is set too high. Autopilot hides node detail you may later want. I would flip from Autopilot to Standard the first time an agent needs host access.

Three autoscalers, one rule

The HPA adds pods, the VPA changes requests, the Cluster Autoscaler adds nodes. They chain, and they can fight.

HPA

Replicas follow CPU

Target 50% of the request, 2 to 8 replicas, scale up fast, scale down one pod a minute after a five minute window. On kind the test asserts it scales past the minimum of 2 under load; it reached 4 at the assertion and 8 in a longer run.

k8s/app/hpa.yaml

VPA

Requests follow usage

Recommendation only. If the VPA changed CPU requests while the HPA divides by them, the two would chase each other. The test fails the build if both drive CPU with the VPA on Auto.

k8s/app/vpa.yaml

Cluster Autoscaler

Nodes follow pending pods

Per-zone bounds on a regional pool, so three zones means three times the number you type. The planner below shows when pods stay Pending because the ceiling is reached. Not runnable on kind; it is a GKE node pool setting.

What is verified

Run

On a real Kubernetes

HPA scale-out, VPA recommendation, RBAC allow and deny, Pod Security restricted, a NetworkPolicy deny from another namespace, StatefulSet reschedule, backup and restore. scripts/kind-test.sh runs in CI on every push.

Checked

Without a cloud

Terraform fmt and validate, a trivy scan with zero high or critical findings, manifest cross-references, 30 Python tests, JavaScript parity.

Not run

Needs a Google project

terraform apply, Workload Identity token exchange, the Google load balancer, Managed Prometheus alerts, Backup for GKE, Cloud Build and Argo CD. Dataplane V2 enforcement of NetworkPolicy is not exercised; kind's own CNI was.
